| ID | Issue | What went wrong | Required correction |
| --- | --- | --- | --- |
| **LL-01** | Frame-level random split | The VAE trainer uses `random_split()` across all HDF5 feature rows (`trainer_vae.py`). Frames from the same video can appear in both training and validation. | Split by recording or drive ID before assigning frames to training, validation, calibration, and test. |
| **LL-02** | Validation leakage | Adjacent frames are highly correlated. Validation performance can look better than performance on genuinely unseen recordings. | Use complete, independent recordings for validation. |
| **LL-03** | Calibration leakage | The Mahalanobis script splits each recording into an early 90% and a final 10%, while VAE training randomly samples from the entire feature pool. The calibration partitions therefore overlap the VAE's training/validation population. | Use dedicated calibration recordings not used to fit the VAE. |
| **LL-04** | Environmental imbalance | The recordings may represent different road types, weather, lighting, traffic, and scene complexity. A naive recording-level split could place these conditions unevenly across the four partitions. | Inventory the conditions first, then create a stratified group split. |
| **LL-05** | No documented split manifest | The current pipeline does not establish one authoritative assignment of every recording to a dataset partition. | Create a manifest recording the recording ID, conditions, partition, and relevant frame metadata. |
| **LL-06** | No established independent final test | Model selection and threshold calibration need to be separated from the final performance evaluation. | Keep a held-out set of complete recordings for final evaluation; do not use it to select checkpoints or thresholds. |
| **LL-07** | Beta configuration inconsistency | The command-line override correctly used `beta=0.0001`, but the YAML training default is `1.0`. A future run without the override could silently use a different beta. | Make the chosen beta explicit in the experiment configuration and record the actual value in run metadata. |
| **LL-08** | Checkpoint path consistency | Training and evaluation may use different checkpoint directories. The filename includes the beta, but that does not ensure the evaluator loads the correct file. | Verify the absolute training output path against the evaluation input path. |
| **LL-09** | Incomplete extraction metadata | The HDF5 stores image basenames rather than full relative paths. The recording ID is recoverable from the filename, but the dataset is harder to audit and reproduce. | Record full relative path, recording ID, frame ID, camera, and split assignment in the manifest. |
| **LL-10** | Limited-extraction allocation bug | In `01_extract_features.py`, the HDF5 allocation size is computed before an optional sample limit is applied. A limited run can leave unused rows in the allocated datasets. | Correct the allocation logic before using limited or dry-run extractions; verify that the row count equals the number of extracted features. |
